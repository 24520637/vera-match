# Independent recovery and closure preparation

This candidate adds working technical controls and synthetic acceptance tests. **It is not final production approval.** The owner explicitly approved signing the exact consent/minimization content on 2026-11-24; the signed files and protected operator signing key are outside Git. Installing those approvals and real staff configuration, final retention/identity minimization, deployed infrastructure and release-candidate acceptance remain required. The original C095 no-journal restore is retained as a negative control with the test journal disabled.

## Independent restriction journal

`ops/recovery-journal` is a separate dependency-free Node.js service. Run it on a separate protected host/storage/credentials boundary, outside application database backup/restore scope. Its API can append an authenticated, bounded, pseudonymous restriction intent and read authenticated signed checkpoints/pages; it has no network edit/delete endpoint. Ed25519 signing material exists only on that host. API clients receive its public key and a 256-bit access token in host-owned files.

Each append is hash chained, sequenced and fsynced before acknowledgement. Idempotent replay of the same intent returns the same record; conflicting reuse is rejected. Startup rejects missing/torn/altered/wrong-identity history. A writer lock rejects a second writer. A hard-killed process may leave a stale lock: establish that no writer exists before an authorized operator removes that lock. Never delete/reinitialize the journal to make a restart succeed.

Client checkpoints bind a fresh random challenge, journal identity, sequence, head hash and issuance time. Clients verify signatures, freshness, every chain link and paginated bounds. The service is the independently trusted current authority: do not roll it back alongside the application. A valid-prefix rollback of *both* the authority and an old application backup is outside that trust assumption and requires independent retained high-watermarks/backup custody. The implementation is not evidence of geographically replicated journal durability, encrypted storage or tested journal-host disaster recovery.

Production API startup requires `RECOVERY_JOURNAL_CLIENT_CONFIG`, validates configuration and replays before opening a listener. Every source restriction writes a journal intent and a database receipt in the same transaction as the actual mutation. A failed/ambiguous journal acknowledgement closes ordinary API requests until isolated recovery. Ordinary requests/readiness also verify a fresh signed connectivity checkpoint, cached for at most five seconds, with a bounded four-second network timeout. Liveness remains available. Test/development does not install a production provider implicitly. Keep both hosts' clocks synchronized: checkpoint freshness is bounded and future clock skew above one second is rejected.

Current capture points cover closure, consent OFF, profile visibility OFF, blocking, logout/all-session revocation, password reset, video deletion, claim revocation, declined matching, returned QA review, staff directives/MFA events and moderator-grant revocation. Privileged direct SQL edits or alternate/new mutation entry points are not supported production workflows and must receive the same capture review.

## Conservative replay

Before its first production start, an authorized operator must explicitly bind the migrated database to a *new, empty* journal using `npm run recovery:initialize -- --database-fingerprint SHA256 --initialize`. The fingerprint is computed by the existing `staffDatabaseFingerprint` helper from the privately loaded DATABASE_URL; never put that URL/password on the command line. This writes a DATABASE_BASELINE entry and an immutable database binding/receipt atomically on the database side. API bootstrap never initializes a database automatically. A genuine backup from before this binding is rejected even if its old sessions/consents would otherwise resolve. A nonempty journal cannot be rebound with the initialization command. Ambiguous/failed initialization requires operator reconciliation, not deleting history or rerunning a reset.

A receipt committed in the same database transaction proves the journal entry was applied. A receipt lost in an older backup, including a PREPARED intent whose original transaction rolled back, is replayed conservatively. Under ordered User locks, the affected accounts lose sessions and reset/verification tokens, members receive real consent OFF events/tasks through the consent coordinator, and eligible non-CLOSED/non-DELETED accounts become SUSPENDED. CLOSED barriers are never reopened. Unknown subjects from registrations newer than the backup do not create replacement identities.

Quarantine deliberately requires support review; it does not reconstruct a missing closure/staff decision or issue new credentials. Reconciliation receipts and audit records are atomic and immutable. Repeated replay does not repeat minimization/events for an acknowledged entry. A mismatched/ahead receipt, invalid checkpoint, changed head during replay or provider failure keeps startup closed. Use exactly one API process and stop the old writer before cutover. No unrestricted proxy trust or distributed rate-limiter guarantee is added.

The new PostgreSQL acceptance test executes a native pre-restriction dump, independently journals the later restriction, restores into a nonce-owned fresh database, reproduces the revived session/consents as a negative control, then proves revocation/OFF/quarantine and idempotent immutable receipts. It also tests the independent record surviving a rolled-back source transaction and the closed fence after transport loss. No developer/shared schema is reset.

## Closure coordination

The existing media consumer still waits for cancellation receipts, native provider absence and genuine capability expiry. A new worker requires an exact signed minimization policy and real journal evidence before processing its remaining domains. It holds the CLOSED User barrier, rechecks the policy before commit and refuses open safety/dispute holds.

- MATCHING: remove mutable member data/display name with revision increments; invalidate pairs and clear mutable score/reasons. Keep immutable choices/audit restricted.
- REVIEW_CLAIMS: require cancellation completion; clear unsubmitted DRAFT content and observations/unpublished claims. Retain submitted reviews, QA decisions, disputes and approved claims with source-loss restrictions pending retention.
- SAFETY: retain restricted blocks, case and immutable moderation evidence under the explicit approved minimization contract. Do not silently unblock or invent staff events.
- RECOVERY: require an independently authenticated closure intent and its APPLIED source receipt, and retain the signed checkpoint in the domain evidence.

Each domain has an immutable closure-bound receipt, exact policy envelope/digest and minimal aggregate evidence; a database trigger refuses a non-media ACK without its receipt. The transaction advances to RETENTION_PENDING/revision 2 only after all five consumers are acknowledged, and writes the actual closure event. The status endpoint distinguishes cleanup pending from retention pending and never claims final erasure. Missing approval/holds/failure leave work pending; worker scheduling moves past held cases and receipts remain the completion authority.

The policy verifier accepts only the documented exact actions, current bounded Ed25519 approvals and non-placeholder authority/legal references. It rejects arbitrary purge instructions, drafts, tampering and erasure claims. Production closure availability requires this approval and a verified recovery service rather than a boolean flag. Read [the owner review](production/OWNER-REVIEW.vi.md) before signing; final retention/purge and post-status-window identity minimization are still separate required work.

## Host preparation

1. Select the actual journal HTTPS origin. Run `node ops/recovery-journal/setup.cjs --directory ABSOLUTE_NEW_DIRECTORY --origin https://journal.YOUR_DOMAIN` on a trusted operator machine. The directory must be outside the checkout; setup refuses overwrite. Protect it with OS ACLs. Never put it in the source archive or chat.
2. Transfer only `server/` to the independent host and install with `bash deploy/install-journal.sh /absolute/generated/server` as its operator. Node.js 24/systemd are prerequisites. Validate the nginx template, obtain TLS and restrict ingress to the API host. The installer is new-host-only and never migrates an app database or provisions paid resources.
3. Transfer only `client/` to `/etc/vera-match/recovery` on the API host (`root:vera`, directory 0750, files 0640). Set `RECOVERY_JOURNAL_CLIENT_CONFIG=/etc/vera-match/recovery/client.json`. The signing private key must never be copied to this host.
4. Install the reviewed consent/minimization/staff approvals with their trusted public keys. Inspect and apply the three additive receipt/binding migrations under the approved database backup/recovery plan. Bind only a fresh unbound deployment using the explicit initialization command above, then take a verified post-binding backup. Keep RESTORE targets isolated and never initialize/rebind a restored database to clear a fence.
5. Build and run the full candidate checks. Run host preflight, real HTTPS smoke, SMTP delivery, storage access/CORS, staff MFA, monitoring/paging and synthetic recovery/cutover acceptance before admitting real users.

Node.js/Windows tests and a source archive do not verify a Linux host installation, DNS/TLS, provider delivery, backup encryption/ACLs or measured RPO/RTO. See [deployment audit](DEPLOYMENT-AUDIT.md) for executed checks and [upload handoff](../deploy/UPLOAD-GUIDE.md) for application service commands.
